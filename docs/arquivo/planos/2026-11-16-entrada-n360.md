# Entrada do n.360 (ver os projetos sem entrar em nenhum): plano de implementação

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** O Início do n.360 vira a lista dos projetos que a pessoa alcança, sem projeto ativo, com a situação de cada um aberta no lugar e a entrada no módulo como ato explícito ("Abrir no n.x"); ninguém é redirecionado em silêncio no boot.

**Architecture:** Só frontend, sem mudança de servidor nem migration. `frontend/src/views/painel.js` troca a visão de projeto do Início (`telaDoN360`) e a alternância Projeto/Carteira (`vistaDoN360`, `n360_vista`) por uma lista montada com `montarLista` sobre `GET /api/v1/carteira`; "Ver situação" pede `GET /api/v1/projects/:id/painel` (sem `?modulo`) só ao abrir a linha, com o cache de 60 s de `S.painel`, sem tocar `S.activeProject`. O cliente (preso ao `client_project_id`) vê o projeto dele já aberto. O boot (`frontend/src/globals.js`, `initApp`) passa a mandar todo mundo do n.360 ao Início, e o item solto `#nav-ot` sai do menu (o n.ot abre pelo botão da linha).

**Tech Stack:** SPA em JavaScript sem framework (Vite empacota; ações por `data-action` e funções em `window`), Vitest 4 com jsdom (`frontend/test`), Playwright em Chromium (`frontend/e2e`, API simulada por `page.route`).

**Spec:** `docs/superpowers/specs/2026-11-14-entrada-n360-design.md` (caminho A, aprovado pelo dono em 14/11/2026), dentro de `docs/superpowers/specs/2026-11-14-n360-posicionamento-e-fluxo-design.md` (seção "Entrada do n.360"). As três confirmações ficam com a opção recomendada: (1) a situação abre na própria linha; (2) o cliente com um projeto só vê a situação já aberta; (3) "Minhas aprovações" aparece como quadro no topo do Início da equipe quando há pedido esperando a pessoa.

Pedido do dono, textual: "ver a situação do meu projeto sem ter um projeto escolhido, não entrar conectado a um projeto".

## Global Constraints

- Nada muda no servidor (`src/`), em `schema.sql` ou em migration. As rotas usadas já existem: `GET /api/v1/carteira` (`src/routes/painel.ts:51-60`), `GET /api/v1/projects/:projectId/painel` (`src/routes/painel.ts:18-42`) e `GET /api/v1/pedidos` (`src/routes/pedidos.ts:175-195`).
- Não há projeto ativo no Início do n.360. Entrar no Início não pede `/painel` de projeto nenhum e não grava `niso_activeProject`. O último projeto usado continua em `localStorage` (`niso_activeProject`, hidratado por `frontend/src/state.js:33`) só para o seletor oferecê-lo primeiro.
- Entrar num projeto só por clique: "Abrir no n.iso", "Abrir no n.privacy", "Abrir no n.ot" (`painelAbrirProjeto`), o botão do item mais urgente da situação (`painelAbrirItem`) ou a escolha no seletor da barra lateral.
- P0-1 do n.ot: o botão "Abrir no n.ot" e a linha do n.ot na situação só aparecem quando o servidor mandou o módulo (`modulos` da linha da carteira, que já vem cortado por projeto E pessoa em `src/services/painel.ts:599`, ou o bloco `modulos.ot` do painel). Nunca deduzir o n.ot de `S.projects`.
- O cliente (`org_admin`, `org_user`, `client` com `client_project_id`) nunca vê outro projeto: o Início dele só pede `GET /api/v1/projects/<client_project_id>/painel` e nunca a carteira.
- Todo texto vindo do servidor passa por `escapeHTML` (em `painel.js`, pelo atalho `e`). Sem handler inline (`onclick=`), sem `<script>` inline, sem `style=` novo: a catraca `frontend/test/catracas-visuais.test.js:97-115` dá teto 0 a `src/views/painel.js`, 84 a `src/globals.js` e 4 a `src/produto.js`, e nenhum desses números pode subir.
- Uma ação primária por tela (um `.btn-primary` visível). Nenhum estado só por cor (`estado()` sempre escreve o rótulo).
- Ações por `data-action="nome"` com a função em `window.nome` (despacho em `frontend/src/delegation.js`); para receber o botão, `data-arg-el`.
- Lista só por `montarLista` (`frontend/src/lista.js`): busca sem acento, "N de M", 25 por vez.
- Texto de tela em português, sem itálico, sem emoji, sem travessão. Marca dos módulos: `n.iso`, `n.privacy`, `n.ot`.
- Ficam como estão: `?tela=` do n.360 (`telaPedida`), o pedido vindo do n.360 num módulo (`pedidoDoHub`), os endereços `/iso`, `/privacy`, `/ot`, o filtro do painel levado ao módulo por `sessionStorage` (`n360_filtro`, `frontend/src/produto.js:158`), o clique do sino no n.360 (`frontend/test/aviso-hub.test.js` já roda com `S.activeProject = null`) e o Stakeholder indo a "Minhas aprovações".
- Testes do frontend: `cd frontend && npx vitest run <arquivos>`. E2E: `cd frontend && npm run build && npx playwright test e2e/<arquivo>` (neste contêiner, com `PW_EXECUTABLE_PATH=/opt/pw-browsers/chromium-1243/chrome-linux64/chrome` na frente; rodou verde na HEAD 725c3b9 para `e2e/n360.spec.js`, 6 de 6).
- Dois PRs, como a spec pede: PR1 = Tasks 1 a 4 (o Início como lista, o seletor, o cliente, o quadro de aprovações); PR2 = Tasks 5 a 7 (o boot sem redirecionamento, o menu, o roteiro E2E e a limpeza). Cada Task deixa `npx vitest run` do frontend e o E2E que ela toca verdes.

**Ordem:** a spec pediu (a) boot e estado, depois (c) lista; aqui (a) e (c) viram a Task 1, porque o Início sem projeto ativo só existe quando a tela deixa de precisar de um projeto (a visão `telaDoN360`), e separar deixaria uma Task com o Início quebrado. O código que cada Task deixa sem uso sai na própria Task; a Task 7 fica com o roteiro E2E e o que sobra.
